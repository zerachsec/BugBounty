## 1. What is IDOR

IDOR happens when an app exposes a reference to an internal object — a user ID, order ID, invoice number, file ID, GUID — and the server never re-checks whether the person making the request actually **owns** that specific object.

It isn't about the ID itself. It's a **broken authorization check** on the backend. Almost every app correctly checks *"is this person logged in?"* (authentication) — but a huge number forget to check *"is this person allowed to touch THIS specific resource?"* (authorization). That gap is IDOR.

> **The one question to ask on every request:**
> *"Does the server verify I own this object, or does it only verify I'm logged in?"*

**Why it's the best Day 1 bug:** IDOR requires zero payload crafting, no filter bypass knowledge, no encoding tricks to start. You need two accounts and a willingness to swap numbers in Burp Repeater. It rewards patience and thoroughness over cleverness.

**Why it keeps happening in 2026 apps:** Modern apps are built from dozens of independent API endpoints and GraphQL resolvers, often written by different developers or generated by scaffolding tools. Every single one needs its own ownership check written by hand. Miss it in *one* resolver out of two hundred, and you have a bounty. Microservices and GraphQL make this worse — ownership logic that lived in one place in an old monolith is now duplicated (or forgotten) across dozens of services.

## 2. The 8 Flavors of IDOR

| Type | What Happens | Example |
|---|---|---|
| **Classic / Visible** | Response directly returns another user's data | `GET /api/user/1002/profile` as user 1001 returns 1002's data |
| **Blind IDOR** | No data in response, but the action still executes | `POST /delete-account?id=1002` returns generic "success" — account is actually deleted |
| **Body / JSON IDOR** | ID hidden in POST/PUT body instead of the URL | `{"user_id":1001,"action":"update_email"}` |
| **GUID / UUID IDOR** | Dev assumed "unguessable" = "secure" — but the GUID leaks elsewhere | GUID shows up in a public post's metadata or a shared link |
| **GraphQL IDOR** | Object ID passed to a resolver with no ownership check inside it | `mutation addTagToAsset(assetId: "gid://...")` |
| **Method-mismatch IDOR** | GET is protected; DELETE/PUT/PATCH on the same path isn't | `/api/order/1002` blocks GET, allows DELETE |
| **Horizontal** | Access another user's data at the *same* privilege tier | User A reads User B's invoice |
| **Vertical** | Reach a *higher*-privilege object via direct reference | Regular user hits an admin-only object by ID |

## 3. Where to Look in a 2026 Stack

Old server-rendered apps hid IDs in URLs. Modern React/Vue + REST/GraphQL apps hide them differently:

1. **REST JSON bodies** — check request AND response for `id`, `user_id`, `uid`, `account_id`, `_id` (Mongo-style), `ref`
2. **GraphQL resolvers** — #1 IDOR source in 2026 stacks; check every `id:` argument in every query and mutation
3. **File/document endpoints** — `/download?file_id=`, `/invoice/123.pdf`, `/export?report=`
4. **Multi-step flows** — checkout wizards, onboarding, password reset — ownership often checked on step 1 only
5. **Mobile app APIs** — same backend as web, far fewer hunters test it, weaker rate limiting
6. **WebSocket messages** — object IDs sent client→server with no server-side ownership re-check
7. **Second-order IDOR** — an ID "safe" in one feature leaks via another — support chat, PDF metadata, search autocomplete
8. **Bulk/batch endpoints** — `/api/bulk-delete` with an array — check if *every* ID is validated, not just the first

## 4. The Hunting Loop

1. **Map every object reference** — browse the whole app logged in, note every ID in URLs, JSON, hidden fields, GraphQL variables.
2. **Get two accounts** at the same privilege level. Non-negotiable — you need a real victim object.
3. **Baseline the request** as Account A in Burp.
4. **Swap the ID** to Account B's, keep Account A's session/token, send in Repeater.
5. **Read the full response** — not just the status code. A 200 with a small body can still leak data in a nested field or header.
6. **Test every HTTP method** on the same endpoint — GET may be protected, DELETE/PUT often isn't.
7. **Test the write path**, not just read — modifying/deleting another user's data pays more than viewing it.
8. **Decode "unguessable" IDs** — try `base64 -d`, check for sequential patterns underneath.
9. **Hunt for the ID elsewhere** if it's not visible directly — public profiles, shared links, JS source, error messages.
10. **Automate the blast radius** with Burp Intruder once you confirm the pattern — affected-user count drives severity.

## 5. Bypass Techniques

### "Unguessable" GUIDs / UUIDs
Developers often think a GUID is safe because it can't be brute-forced. But the GUID still has zero ownership check behind it — you just need to *find* a victim's GUID once. Check: public share links, PDF/image metadata, autocomplete/search endpoints, error messages, and old API versions that might still expose sequential IDs for the same object.

### Encrypted / Hashed IDs
Some apps hash or encrypt the ID client-side. Try changing just one character and observing the error — a generic 500 vs. a clean "not found" can reveal whether the value is even being validated cryptographically or just pattern-matched.

### Rate Limiting on Enumeration
If direct brute-force is blocked, look for the ID leaking through a different, unthrottled endpoint (e.g., an autocomplete search box that returns IDs in its response even though the direct object endpoint is rate-limited).

### Front-End Masking
The UI might display a friendly slug (`/user/john-doe`) while the backend API called by the page still uses the raw numeric ID underneath — check Burp's history for the actual XHR/fetch calls, not just the visible URL.

### Header-Based Access Control Bypass
Some access control is enforced only at a reverse proxy/router layer. Try spoofing headers like `X-Original-URL`, `X-Rewrite-URL`, or `X-Forwarded-For` to see if the backend re-derives a different (unprotected) route.

## 7. Report Template

```markdown
## Title
IDOR in [endpoint] allows [horizontal/vertical] access to [resource]

## Summary
[App] does not verify object ownership on [endpoint], allowing an
authenticated user to [view/modify/delete] another user's [resource]
by changing [parameter].

## Steps to Reproduce
1. Log in as Account A ([email/username])
2. Perform [action], intercept the request in Burp Suite
3. Replace [parameter]=[Account A's ID] with [parameter]=[Account B's ID]
4. Observe the response returns/modifies Account B's data

## Request
[redacted PoC request]

## Impact
- Confidentiality: [what data is exposed]
- Blast radius: [tested against N sequential IDs]
- Chainable with: [e.g. password disclosure -> full account takeover]

## Remediation
Verify server-side that the authenticated session owns the requested
object ID before returning or modifying data — on every endpoint,
every HTTP method.
```

## 8. Real Disclosed Reports — Low to High

### 🟢 $175 — HackerOne: GraphQL IDOR
**AddTagToAssets mutation — private tag disclosure**
A GraphQL mutation took a base64-encoded `tagId`. Decoding it revealed a predictable internal format; swapping the decoded value exposed another user's private custom tags with zero victim interaction. Low payout — narrow data (tag names only), and it required decoding an obscure GraphQL ID.
🔗 hackerone.com/reports/2633771

### 🟢 $1,500 — RedTube: Destructive IDOR
**Delete any user's photos and albums**
A logged-in user could delete photos and entire albums belonging to other users by directly referencing gallery/photo IDs, with no server-side ownership check. Mid-low payout — destructive but non-financial, non-PII content.
🔗 hackerone.com/reports/380410

### 🔵 $5,000 — Vimeo: Account Takeover Chain
**IDOR in password reset flow**
The password reset mechanism referenced objects (reset tokens/requests) in a way that let an attacker manipulate the flow to reset another user's password. Higher severity — leads directly to account takeover, not just data exposure.
🔗 hackerone.com/reports/42587

### 🟠 $10,000 — Uber: Non-Numeric Identifier
**IDOR via phone number instead of user ID**
The vulnerable endpoint accepted a phone number — not a numeric userID — as the object reference for ride/account lookups. Key lesson: any unique identifier tied to an account can be the vulnerable parameter, not just fields literally named "id".
🔗 hackerone.com/reports/143717

### 🔴 $10,500 — PayPal: Business Account Compromise
**IDOR to add secondary users to any business account**
The endpoint for adding secondary users to a PayPal Business account never verified the requester owned the target business account ID — allowing an attacker to add themselves to any business account on the platform. Highest payout: financial platform, full account-level compromise, high-value business accounts.
🔗 hackerone.com/reports/415081

## 9. Quick Reference Cheat Sheet

### Parameters to Always Test
- `id`, `user_id`, `uid`, `_id`
- `account_id`, `order_id`, `invoice_id`
- `file_id`, `doc_id`, `ref`, `token`
- Any GraphQL variable ending in `Id`

### Never Skip
- POST/PUT/PATCH/DELETE — not just GET
- Full response body — not just status code
- Mobile API endpoints
- Redirect responses (data can leak before the redirect)

### Severity Boosters for Your Report
- Write access (not just read)
- PII or financial data exposed
- Works with zero victim interaction
- Large blast radius (tested across N IDs)

### Tools
- Burp Suite — Repeater + Intruder
- Two test accounts, same privilege tier
- CyberChef / `base64 -d` for encoded IDs
- Autorize / Auth Analyzer (Burp extensions)
